# Автоматическая смена провайдера для заданий очереди

Дата: 24 ноября 2026. Основа: PR #15, `4210ba85f111095523f6c25d1f8d8ad819fcd2fa`. Проверенные исходники: `b690796`; этот отчёт добавлен после живой проверки.

## Результат

Обычное задание может явно разрешить `providerSwitchPolicy: recent-messages`. Когда наступит время запуска и снимутся ожидания, сервер переключит существующий диалог на назначенного провайдера, соберёт контекст по актуальной истории и отправит задание обычным путём. По умолчанию действует `manual`: назначение модели само по себе не разрешает автоматическую передачу истории.

В форме «Назначить модель заданию» появился отдельный флажок с объяснением объёма передачи. При выборе другого провайдера он сбрасывается. Изменение сохраняется кнопкой редактора; отмена формы восстанавливает исходный выбор при следующем открытии, включая компактный drawer. Отметка автоперехода видна в строке очереди даже при длинном имени модели.

SDK `threads.queuedMessages.create/update` принимает `providerSwitchPolicy`; CLI `thread queue create/update` — `--provider-switch-policy manual|recent-messages`. Табличный вывод показывает это правило. Переназначение без нового явного правила возвращает ручной режим. Изменение только правила сохраняет параметры исполнения и позволяет отозвать разрешение даже при отключённом провайдере. Сам запуск повторно проверяет целевую модель.

Бюджет передачи — до 8192 токенов по существующей консервативной оценке UTF-8-байтами, дополнительно ограниченный четвертью окна, объявленного каталогом модели. Передаются последние видимые тексты. Скрытый ввод, рассуждения, результаты инструментов и содержимое вложений исключаются; распознанные учётные данные маскируются. Неполная история не выдаётся за полную.

## Порядок и восстановление

Плагины получают назначенный `requestedExecution.providerId`, а `thread` описывает фактически текущего агента. Переход начинается после допуска плагинов и проверок времени, хоста, активной работы и взаимодействий. Задание не перенаправляет активный ход другому провайдеру; cross-provider steer отклоняется. Повторы прежних сессий, служебные уведомления и старые строки без явного назначения не могут включить автопереход.

Используются существующие preview, commit и журнал переходов. Владелец claim атомарно сохраняет внутренний UUID операции в задании. Незавершённая операция сначала восстанавливается; новую разрешено начать после подтверждённого терминального исхода. Запись очереди изымается в транзакции создания запроса хода. Завершённый переход не означает повторной отправки уже изъятого задания.

Блокировка проверки плагинов удерживается до подготовки провайдера и допуска хода, поэтому следующий диалог видит актуальное число работающих диалогов. Ожидание ответа самой модели в эту блокировку не входит. Медленная подготовка исполнителя может задерживать другие отправки, проходящие через тот же общий барьер.

Миграция **170** добавляет `provider_switch_policy` с исходным значением `manual` и внутренний `provider_switch_operation_id`. Старые назначения и неизвестный источник сохраняются. Группировка требует совпадения назначения, исходного поколения, правила передачи и операции. Изменений команд или полей host-daemon wire нет; версия протокола **283** сохранена. Руководство CLI, Plugin Guide и API audit обновлены.

Регрессии сначала воспроизведены на владельцах поведения, затем исправлены:

- Первый запуск задания на уже назначенном провайдере ошибочно обращался к строке после её изъятия при admission. Тест сначала получил `Queued message claim expired`.
- Пока первый диалог готовил целевую сессию, второй мог пройти ограничение числа запусков. До исправления проверка действительно зарегистрировала лишний пользовательский запрос второго диалога.
- Отзыв разрешения зависел от доступности назначенного провайдера. Настоящий SDK сначала вернул 409 для отключённого провайдера.
- Компактный drawer сохранял отменённое локальное состояние формы. Общая таблица desktop/compact сначала упала только для compact: флажок оставался включённым вместо исходного выключенного. Новый идентификатор открытия сбрасывает форму, сохраняя сам drawer.

Дополнительно проверены время, удержание плагином, активный ход, отключённый хост, свежий контекст, потеря claim, удаление во время подготовки, подтверждённый откат перед новой попыткой и восстановление сохранённой committed-операции после повторного подключения исполнителя. Базы настоящие, с реальными миграциями.

Журналы находятся в `.tmp/toolchain/test-queue-provider-transition-*.log`, `test-queue-transition-*.log`, `build-queue-provider-transition-*.log` и `build-queue-transition-mobile-cancel.log`. ## Настоящее приложение и модели

Проверка выполнена на macOS в отдельном checkout, с новой помеченной базой, собственными портами, временным Git-проектом, отдельным браузерным профилем и конфигурацией Pi. Исходная `qwen2.5:7b` не изменялась: использовался производный алиас с `num_ctx 32768`.

1. Настоящий Codex запомнил контрольную фразу без изменения файлов. Созданы два отложенных задания. Через UI первое назначено Pi/Qwen с явным полным доступом и флажком автоперехода; второе осталось Codex и получило правило через CLI. До срока активный агент остался Codex, запрос был один, файлов ещё не было.
2. На desktop и ширине 390 проверены форма, сохранённый черновик и отсутствие `inert`/`aria-hidden` у корня. Живая мобильная проверка выявила ошибку отмены; после исправления повторное открытие восстановило сохранённый флажок. Ответы API до и после отмены полностью совпали, включая версии и сроки заданий.
3. Перезапуск server/daemon/app сохранил обе модели, правила, сроки и основной неотправленный черновик.
4. Сроки заданий перенесены на ближайшее время. Сервер автоматически выполнил Codex → Pi/Qwen. Запрос Qwen не содержал самой контрольной фразы: модель получила её из переданного контекста и настоящим инструментом записала `queue-qwen.txt`. Ollama `/api/ps` подтвердил обслуживаемое окно **32768**.
5. При возврате на Codex первая подготовка подтвердилась, затем операция откатилась с `provider_transition_interrupted`. Она началась через 35 мс после завершения Qwen. Детальная причина этого отката из существующих логов не установлена. Задание сохранилось и примерно через 17 секунд после отката автоматически выполнило новую операцию. Codex прочитал файл и побайтно записал `queue-codex.txt`; команда завершилась с кодом 0. Оба файла содержали точную фразу и один перевод строки. Пользовательских запросов было ровно три.
6. Дополнительный цикл проверил чтение обоих файлов: Qwen вызвал `read`, Codex прочитал второй файл. Возврат на Codex после паузы прошёл с первой попытки. Содержимое, размер и время изменения исходных файлов не изменились.
7. После ещё одного перезапуска осталось ровно **пять разных запросов**, ноль отклонённых запросов, пустая очередь и один видимый диалог в прежнем workspace. Журнал содержит четыре завершённых перехода и один подтверждённый откат. Черновик сохранился. Финальные screenshots 1440×1000 и Chromium 390×844 просмотрены.

Свидетельства: `.tmp/verify-queue-transition-20261124/`, включая `execution-summary.json`, `read-check-summary.json`, `post-restart-summary.json`, `completed-items-final.json`, `ollama-serving-window.json`, снимки до/после исправления отмены и `cleanup.json`.

Собственный браузер и точно установленные dev runners остановлены. Все пять выделенных портов свободны. Удалены только помеченная тестовая база, временный Git-проект и производный алиас модели; исходная Qwen сохранена. Checkout и доказательства оставлены.

## Границы

Зависимости между заданиями и параллельные рабочие ветки ещё не реализованы. Исторический откат первого возврата сохранён в отчёте и ленте; безошибочный первый проход всех native-переходов не заявляется. Safari/iPhone заблокирован отсутствующим iOS Simulator (`unable to find utility simctl`); Chromium на мобильной ширине его не заменяет. Linux, Android, VPS и другие облачные провайдеры в этом изменении не проверялись. Остальные пункты roadmap остаются в работе.
