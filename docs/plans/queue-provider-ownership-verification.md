# Проверка назначения заданий очереди

Дата: 24 ноября 2026. Основа: `e0bd40f59f6719478bd69a0ff205906c8fd8415c` (PR #13). Живая проверка выполнена на исходниках `51fccf41d1a6c814066ce182e7df011b48fd6135`; после неё добавлен этот отчёт.

## Поведение

Новые пользовательские задания сохраняют провайдера, которому они были назначены. Если диалог переключён на другого агента, наступление срока или ручная отправка оставляют задание в очереди с объяснением. Возврат к тому же провайдеру разрешает обычное задание в новой сессии. Повтор неудавшегося запроса требует исходного поколения сессии: продолжение нельзя незаметно перенести в новую историю агента.

Группировать можно только соседние задания одного провайдера и поколения. Проверки действуют при создании, изменении параметров, подготовке отправки и атомарном изъятии из очереди. Решение плагина о повторе также защищено от одновременной смены контекста. Текст задания можно исправить при другом активном провайдере; редактор показывает исходного агента, а несовместимые элементы выбора модели и разрешений доступны только для просмотра.

Миграция 169 добавляет `provider_id` и внутренний `provider_session_id`. Старые строки остаются с `null`: их источник ранее не записывался. Служебные уведомления следуют текущему агенту. В UI, SDK, CLI и событиях очереди доступен nullable `providerId`; внутреннее поколение в публичный DTO не добавлено. Руководство CLI и Plugin Guide обновлены. Поля протокола daemon не менялись, версия остаётся 283.

## Найденные ошибки и проверки до исправления

Регрессии воспроизводились на прежнем коде, затем проходили после исправления:

- Задание Codex отправлялось после смены владельца диалога на Claude Code; одинаковые строки моделей позволяли сгруппировать разных провайдеров.
- Сбой старой сессии мог стать повтором новой; уже поставленный повтор мог отправить продолжение после смены поколения.
- Пока повтор ожидал решения плагина, изменение контекста могло пройти конкурентно.
- Редактор задания Codex показывал имя текущего Pi/Claude вместо назначенного агента.
- У свежей сессии Codex изменение reasoning перед первой отправкой вызывало `thread/resume`, хотя rollout ещё не существовал. Нативная ошибка: `no rollout found for thread id …`.

Последняя ошибка обнаружена настоящей отправкой из очереди. В первой попытке задание было изъято, затем Codex отклонил запрос, файл не появился. Эта попытка не считается успешной. Исправление позволяет заново создать только сессию без попыток отправки. После принятой или неоднозначно завершившейся отправки сохраняется восстановление прежней истории. Таблица регрессии проверяет все три случая через настоящий bridge и отдельный процесс имитации нативного сервера.

## Настоящая проверка UI и исполнения

Использованы отдельный source checkout, помеченное хранилище, проект и временный Git-каталог. Рабочие данные BB пользователя не использовались. Браузер Chromium проверен при ширинах 1440 и 390 пикселей; Safari/iPhone этим не проверены.

1. Codex выполнил начальный короткий запрос. Через CLI поставлено задание Codex с `medium`, записью единственной проверочной строки в `queue-owner.txt` и отложенным сроком.
2. Через интерфейс тот же диалог переключён на Pi с локальным Qwen. Предпросмотр передавал два сообщения истории, без ожидающего задания.
3. После наступления срока задание осталось назначенным Codex с явной причиной ошибки. Новый запрос агенту не отправлен, проверочный файл отсутствовал.
4. В первом проверочном диалоге текст удалось изменить, сохранив назначение и модель. Перезапуск server/daemon/app сохранил очередь, ошибку и текст. Исправленный редактор показывал `Codex`, несовместимые параметры были недоступны, текст сохранялся.
5. После исправления нативного Codex сценарий повторён во втором синтетическом диалоге с тем же workspace. Обратный переход подготовил Codex с `low`; ожидающее задание сохранило `medium`. Штатный повтор очереди отправил его один раз, Codex записал точную строку и ответил `ОЧЕРЕДЬ_ГОТОВА`.
6. Отдельное отложенное задание чтения отправлено кнопкой **Send now** в мобильном меню. Codex прочитал файл и вернул точную строку. Итог: три принятых запроса (начальный, запись, чтение), ноль отклонённых, одна команда записи и одна команда чтения с кодом 0, пустая очередь и idle. Идентификатор диалога и workspace сохранились при обоих переходах.

Оба перехода имеют состояние `completed` в журнале. Замена пустого нативного идентификатора Codex при `low → medium` подтверждена событиями. Мобильный корень не имеет `inert`/`aria-hidden`, ширина документа равна 390 пикселям. Скриншоты рабочего стола, мобильного результата, ошибки и редактора просмотрены.

Доказательства сохранены локально в `.tmp/verify-queue-provider-20261124/`. Собственный браузер и dev runner остановлены; все пять портов освобождены. Удалены только помеченное проверочное хранилище, временный workspace и производный алиас Qwen. Исходная `qwen2.5:7b` и её настройки не изменены.

## Границы результата

Автоматического перехода провайдера по заданию и отдельного выбора провайдера каждого задания здесь ещё нет. Это следующий этап очереди. Переходы проверены с настоящими Codex и Pi, но в этой проверке Qwen не выполнял пользовательский inference; окно 32768 взято из каталога, фактически обслуживаемое окно заново не измерялось. Восстановление пустой нативной сессии Codex после перезапуска daemon до её первой отправки отдельно не проверялось. Linux, Safari/iPhone, Android, VPS и остальные пункты roadmap не считаются завершёнными.
