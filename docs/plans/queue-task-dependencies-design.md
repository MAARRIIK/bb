# Зависимости заданий очереди

Статус: реализовано после PR #18. Выбор зависимостей в UI/SDK/CLI, допуск и долговечные результаты проверены автоматическими наборами и настоящим циклом Codex → Qwen → Codex с перезапуском. [Результаты и ограничения](./queue-task-dependencies-verification.md).

## Поведение

Обычное задание может явно перечислить до 16 заданий того же диалога, успешного завершения которых оно ждёт. По умолчанию список пуст. Удаление строки очереди и состояние idle не означают успех: очередь удаляет строку при допуске запроса, до ответа агента.

Для задачи сохраняется отдельная запись запуска: постоянный ID задания, диалог, исходный и текущий запрос, провайдер и поколение, принятый ход и результат. Исход связывается с реальным принятым запросом, а не с последним сообщением диалога. Новая модель получает контекст перед исполнением после снятия зависимостей.

Состояния записи: queued, running, succeeded, failed, cancelled. Ошибка или отмена предшественника удерживает зависимое задание до решения пользователя. «Отправить сейчас» не обходит эту проверку. Можно изменить зависимости или удалить ожидающее задание. Независимые задания за ним используют существующий механизм пропуска ожидающих групп.

Первая поверхность выбора предлагает существующие обычные задания очереди. Уже выбранная зависимость сохраняется после запуска и удаления предшественника из очереди. Повторы сессии и служебные уведомления не получают собственный список зависимостей. Циклы и ссылка на себя отклоняются. Перестановка меняет приоритет среди готовых задач, сохраняя условия запуска. Группировка требует одинаковых зависимостей и не может объединить задачу с её предшественником в один запрос.

## Транзакции и восстановление

- Создание задания и проверка его зависимостей выполняются одной транзакцией. Проверяются существование, диалог, вид задания и отсутствие цикла; доступ к чужому проекту через ID не раскрывается.
- Изъятие claim и связь записи запуска с новым запросом фиксируются атомарно с допуском хода. Потерянный claim, ручная остановка или смена поколения не создают лишний запуск.
- `turn/input/accepted` связывает запрос с конкретным ходом. Только его завершение с правильным источником может выставить succeeded. Отказ запроса, подтверждённая остановка и удаление ожидающего задания сохраняют соответствующий терминальный исход.
- Изменение записи результата и фиксация принятого события должны быть атомарны либо иметь доказанное восстановление по сохранённым событиям. Сбой между сохранением ответа и последующим побочным эффектом не должен навсегда удерживать зависимые задания.
- Ожидание зависимостей проверяется до смены провайдера и повторно в транзакции допуска. Завершение предшественника будит очередь. Очистка истории не превращает сохранённый результат в неизвестный; удаление диалога очищает его записи запусков.

## Поверхности и проверка

UI, SDK и CLI используют одни create/update поля и серверную проверку. В UI видны выбранные предшественники и причина ожидания. CLI получает повторяемый `--depends-on` и явную очистку; JSON сохраняет IDs. Новые поля заполняются по умолчанию один раз на серверной границе. Миграция генерируется через Drizzle/Turbo, снимки не редактируются вручную.

Проверка должна покрыть успешную цепочку через разные модели, ошибку и отмену предшественника, независимое задание за удержанным, цикл, чужой диалог, изменение порядка/группировки, send-now, steer, первый запуск pending-диалога, потерю claim, повтор после сбоя и перезапуск с сохранённым исходом. Базы настоящие. Живой цикл использует отдельную сборку и временный проект.

## Реализованные решения

Допуск сохраняет реальный requestId вместе с удалением claim в одной транзакции. Сначала проверяется сохранность claim; удаление задания во время подготовки модели отменяет отправку. Первый pending-запрос получает ID из контекста provisioning. Локальные команды контекста не служат заданиями-предшественниками.

Принятое событие связывает текущий запрос с корневым ходом и его источником. Повторный bind уже принятого хода требует того же поколения. Позднее подтверждение проверяет ранее сохранённое завершение этого хода. Изменение результата выполняется вместе с фиксацией события; терминальный успех не переписывается. Отказ до подтверждения и подтверждённая остановка сохраняют failed/cancelled. Повтор исходного запроса обновляет его запись запуска, сохраняя исходный ID.

Проверки зависимостей выполняются перед подготовкой провайдера и повторно в транзакции допуска. Изменение зависимостей требует завершённого перехода провайдера и сбрасывает старую привязку операции. Завершение предшественника обновляет только ожидания зависимостей, сохраняя время отправки и блокировки плагинов. SDK и CLI используют тот же серверный путь, что форма задания.

Индексы рассчитаны на запросы по ID задания, запросу, ходу и состоянию в диалоге. Нагрузочные сценарии отдельно учитывают до 10 тысяч сохранённых результатов. Общая проверка инвентаря навыка всё ещё останавливается на существующем `Unmapped CLI family: diagnostics`; она не считается пройденной.

## Отложено

Первый интерфейс предлагает только живые обычные задания очереди и сохраняет уже выбранные ID после допуска. Выбор произвольного завершённого/выполняющегося предшественника из отдельной истории и политика срока хранения результатов остаются предметом следующего расширения. Проверки iOS Safari, Linux, Android и VPS не подменяются Chromium на macOS.
