# Поколения сессий в хранилище

Ветка: `personal/provider-session-fencing`, основание `b070c0e992f5b1c19f962baced8bff7331f37ccb` — слитый [PR #4](https://github.com/MAARRIIK/bb/pull/4).

## Изменение

Метка провайдера отличает Codex от Claude, но при возврате к Codex прежняя сессия тоже принадлежит Codex. Нужна дополнительная граница, чтобы свежая сессия не возобновляла старый, не синхронизированный контекст.

`threads.provider_session_id` выбирает текущее поколение сессии. `events.provider_session_id` сохраняет поколение события и остаётся исходным при обоих способах копирования истории. Поиск сессии требует совпадения поколения. Полная видимая история сохраняется.

Сгенерированная миграция `0167_provider_session_fencing` добавляет две nullable-колонки. Null обозначает прежнее поколение; старые установки продолжают работать без переписывания истории. Снимок и журнал созданы Drizzle. Сценарии отката старых схем обновлены.

Это внутренняя подготовка хранения. Переключатель и активация нового поколения пока не доступны. Вставка событий исполнителя пока берёт поколение из строки диалога; до включения переключения источник поколения должен пройти через протокол событий, запросов инструментов и подтверждений. Новых пользовательских действий UI/SDK/CLI или полей daemon-протокола на этой стадии нет.

## Проверка

Среда: macOS arm64, Node 22.19.0, pnpm 9.15.0. Использовались настоящие SQLite из штатных миграций; рабочая база BB не затронута.

| Проверка | Результат |
| --- | --- |
| Полный прогон базы | 761 пройден; 2 новых случая первоначально остановились на ошибке тестового помощника |
| Все тесты событий после исправления помощника | 99 пройдены, включая оба исправленных случая; всего 763 разных случая базы прошли в этих прогонах |
| Codex → Claude → Codex в сохранённых строках | Свежая сессия не возобновляет прежний идентификатор; проверено для legacy и явного начального поколения |
| Повторное открытие сериализованной SQLite | Выбрана текущая сессия; все три исторические записи сохранены |
| Копирование истории между одинаковыми и разными провайдерами | Происхождение и поколение сохранены для обычной и переписываемой большой записи |
| Отрицательная проверка фильтра | Без условия поколения оба случая возврата выбирают старую сессию; с условием оба проходят |
| Сервер: владение сессиями, fork, редактирование, очистка, runtime display, кэши столбцов диалога | 167 пройдены, 8 файлов |
| Типы и type-aware lint базы и сервера | Пройдены |

Команды:

```sh
pnpm exec turbo run typecheck lint:type-aware --filter=@bb/db --filter=@bb/server
pnpm exec turbo run test --filter=@bb/db
pnpm exec turbo run test --filter=@bb/db -- data/events.test.ts
```

Журналы находятся локально в `.tmp/toolchain/*provider-session-fencing*`. Полный серверный прогон предыдущего этапа не выдаётся за повторённый для этого изменения.

## Дальше

Передавать поколение от отдельного процесса агента через события и запросы, отбрасывать старые запросы до выполнения инструментов, добавить подготовку целевой сессии с откатом и пакет контекста. Только после этого включить одно действие UI/SDK/CLI и проверить настоящее переключение в неизменном диалоге. Сквозной сценарий с реальными Codex/Claude, Linux, iPhone и VPS этим этапом не подтверждён.
