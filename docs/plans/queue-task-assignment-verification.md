# Назначение модели отдельному заданию

Дата: 24 ноября 2026. Основа: PR #14, `de3d5cde6076dce6829da21aa22023850a541c8b`. Проверенные исходники: `edfefbd`; после живой проверки добавлен этот отчёт.

## Результат

В редакторе ожидающего задания появилась форма «Назначить модель заданию»: провайдер, модель, разрешения, обдумывание и режим обслуживания. Выбор сохраняется вместе с текстом задания. Активный агент диалога при этом не меняется. Отмена формы возвращает исходный выбор. Провайдер и модель видны в строках очереди и в новых колонках CLI.

SDK `threads.queuedMessages.create/update` принимает `providerId`; CLI `thread queue create/update` — `--provider`. При назначении другого провайдера нужны явные модель и разрешения. Каталог, доступность, возможности модели и предел разрешений машины проверяет тот же серверный валидатор, что используется при просмотре перехода в существующем чате. Настройки текущего агента не подставляются в параметры другого провайдера.

Параметры ожидающего задания можно изменить, даже если сейчас активен другой агент. Обычное задание разрешено переназначить; повтор старой сессии и служебное уведомление — нет. Группу сначала нужно разделить. Явное назначение старой строки с неизвестным источником сохраняет выбранного провайдера, включая выбор текущего агента. Переназначение очищает ошибку прежнего провайдера, сохраняя срок отправки и удержание плагином.

При наступлении срока задание другого провайдера остаётся в очереди с объяснением. Перед отправкой нужно переключить чат на назначенного агента через существующий просмотр контекста. Автоматические переходы очереди здесь ещё не реализованы.

Новых миграций и полей daemon-протокола нет; версия 283 сохранена. Обновлены руководство CLI, Plugin Guide и API audit.

## Настоящий интерфейс и хранение

Проверка выполнена в отдельном source checkout на macOS, с новой помеченной базой, временной рабочей папкой, собственным профилем браузера и отдельной конфигурацией Pi. Рабочие данные BB пользователя не использовались.

1. Codex выполнил единственный начальный запрос. Через CLI созданы два отложенных задания: запись проверочного файла и чтение README. В основном композере оставлен отдельный неотправленный черновик.
2. После обновления формы перезапуск изолированного server/daemon/app сохранил исходные задания. Страница после перезагрузки показала прежний черновик.
3. Через UI первое задание назначено Pi с локальным Qwen и явным полным доступом; редактор сохранён. Второе осталось Codex с другим reasoning. Активный агент, идентификатор чата и workspace сохранились. Перезагрузка страницы сохранила оба назначения и черновик.
4. На ширине 390 пикселей у второго задания выбран Pi, затем форма отменена Escape. Повторное открытие вернуло Codex и прежние параметры. После закрытия редактора сервер подтвердил неизменность текста, назначения, reasoning и версии второй строки.
5. При наступлении срока первого задания активным оставался Codex. Задание Pi осталось в очереди с причиной `This message is assigned to pi…`; нового запроса модели и проверочного файла не появилось.
6. Живой CLI `queue update --provider codex` с явными параметрами и новым будущим сроком очистил старую ошибку, сохранив состояние `scheduled`. `queue create --provider pi` создал третье задание Pi, которое также не ушло Codex. Табличный CLI показал разные назначения.

Итог перед очисткой: один видимый диалог, активный Codex в idle, один начальный запрос, ноль отклонённых запросов и ноль переходов провайдера. Проверочный файл отсутствует. Скриншоты desktop 1440×1000 и Chromium 390×844 просмотрены. При открытой исправленной форме основной интерфейс и его предки не имеют скрытия или `inert`; ширина документа на мобильном экране равна 390.

Доказательства находятся в `.tmp/verify-queue-assignment-20261124/`, включая ответы API, сравнение отменённого задания и `summary.json`. Перед завершением удалены три собственных неотправленных задания. Проверочный браузер и точно установленный dev runner остановлены, все пять портов свободны. Удалены только помеченная база, временная рабочая папка и производный алиас модели; исходная `qwen2.5:7b` и её настройки сохранены.

## Ограничения

Qwen не выполнял пользовательский inference в этой проверке; его каталог использовал объявленное окно 32768. Качество ответа модели и фактически обслуживаемое окно здесь не проверялись. Safari/iPhone заблокирован отсутствующим iOS Simulator: `xcrun simctl` сообщает `unable to find utility simctl`. Linux, Android и VPS не проверены. Автоматические переходы, зависимости очереди и остальные незавершённые пункты roadmap остаются в работе.
