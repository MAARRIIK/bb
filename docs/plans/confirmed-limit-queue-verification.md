# Очередь после подтверждённого лимита

Дата: 24 ноября 2026. Основа: PR #21, `e43a3483fa736f5f28c104a740938b811ef3d579`. Проверенные исходники: `48cb2dbaa0e1ed126e1cf3c587841f1504cd3b06`; последующие изменения — только этот отчёт и roadmap.

## Поведение

Provider retry по умолчанию приостанавливает новые задания той же модели после подтверждённой ошибки квоты. Решение использует ошибку, запрос и лимиты текущих провайдера и поколения сессии. Другая модель, другой провайдер и присоединение к работающему ходу проходят обычные проверки. Модель автоматически не подменяется.

Доступность маршрутизированного аккаунта проверяется через существующий RPC `provider-retry.v1.availability`. Готовый аккаунт разрешает отправку; заблокированный пул ждёт сброса; недоступный источник оставляет явное ожидание неизвестной доступности. Снимок локального аккаунта не заменяет неизвестное состояние маршрута. Асинхронный запрос выполняется вне блокировки допуска, объединяет одновременные обращения и обновляется через минуту. Завершение проверки будит очередь.

Для прямого подключения требуется одновременно подтверждённая ошибка rate-limit/429 и заблокированное окно подписки. Предупреждение, баланс кредитов и разрешённый overage не блокируют. Известное время сброса учитывает прежний запас 15 секунд; неизвестное время оставляет понятное ожидание с периодической перепроверкой. Старое измерение 100% само по себе не считается отказом сервиса.

«Send now» — существующее явное разрешение отправки поверх plugin hold; проверки зависимостей и готовности исполнителя сохраняются. Можно изменить назначение задания или выключить `holdQueuedAtLimits` в настройках Provider retry. UI, `bb plugin config provider-retry set holdQueuedAtLimits false` и SDK настроек используют один путь. Прежний `maximumWait` независимо ограничивает планирование автоматического повтора.

Сервер добавляет nullable `MessageDispatchHookContext.experimental_lastFailure` и `ExperimentalDispatchFailure`: метаданные включают фактическую модель неудачного запроса. Core собирает их общим с `turn.failed` владельцем данных в единственной точке допуска перед автоматической сменой провайдера. Контракт описан в Plugin Guide и `docs/api_to_audit.md`; обновлены конфигурационная документация, CLI guide и собственный skill плагина. Host-daemon wire и схема БД не меняются; протокол остаётся **283**.

## Сохранение фактов

Найдена ошибка фоновой очистки: поздний снимок старой сессии вытеснял актуальный лимит, поскольку сохранялся только последний снимок всего диалога. Для неархивного диалога теперь сохраняются последний общий снимок и последний снимок текущих провайдера/поколения — максимум два. Совпавшие снимки занимают одну строку. Архивирование сохраняет прежнюю очистку. Используется индекс миграции 172, новой миграции нет. Уже удалённые прежними версиями факты восстановить невозможно.

Три регрессии на настоящей мигрированной SQLite сначала упали из-за удаления текущего снимка. После исправления проходят варианты с другим провайдером, старым поколением и чужим провайдером в том же поколении, повторным открытием базы, новым актуальным снимком и архивированием.

Отдельный checkout исходников, новая помеченная база, собственные порты, браузерный профиль и одноразовый проект. Принадлежность процессов подтверждена командой, cwd и маркером. Сначала настоящий Codex выполнил короткий контрольный запрос и создал пригодную к продолжению сессию.

1. Настройка выключена настоящим нажатием в UI; CLI прочитал false. Через CLI установлено true; после перезагрузки UI показывает включённое значение. Проверены desktop 1440×1000 и Chromium 390×844: нет горизонтального переполнения, корень не inert/aria-hidden, переключатель виден после закрытия боковой панели.
2. В остановленную одноразовую базу внесён явно контролируемый неотправленный запрос с ошибкой подписки и будущим сбросом. После него добавлен разрешающий снимок старого поколения. Очистка сохранила текущую блокировку. Это моделирование отказа, не настоящее исчерпание подписки аккаунта.
3. Перезапуск и снятие расписания через CLI перевели задание в ожидание Provider retry. В журнале не появился новый запрос. Повторный перезапуск уже удерживаемой очереди сохранил ID задания и восстановил проверку доступности и причину ожидания без нового `turn.failed`.
4. Первоначальный старый снимок тестовой записи содержал недопустимый статус `ok`; проверка схемы отклонила историю. Запись исправлена на `allowed` при остановленном сервере, оставшиеся снимки проверены настоящей схемой. Первый снимок с ошибкой истории не засчитывается. После нового запуска история загрузилась; окончательные screenshot и DOM содержат причину удержания.

## Ограничения

Это допуск после подтверждённой ошибки той же модели, а не предварительное резервирование всех квот аккаунта. Квоты семейств моделей, новые источники, бюджеты и отображение рядом с выбором модели остаются отдельными задачами. Английские строки плагина ещё требуют общего пути локализации. Настоящий исчерпанный аккаунт и маршрутизированный пул в браузере не проверены; их ветки проверены автоматическими тестами. Safari/iPhone, Linux, Android и VPS не проверены. Прежняя ошибка inventory verify-bb `Unmapped CLI family: diagnostics` остаётся открытой; baseline не переписан.
