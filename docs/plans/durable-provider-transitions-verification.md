# Серверный журнал и восстановление переходов

Основание — `8c0469b42a3211949323bf5016217773a53355ef`, слитый [PR #10](https://github.com/MAARRIIK/bb/pull/10).

Подготовленная исполнителем новая сессия должна переживать потерю ответа и перезапуск сервера без потери прежнего владельца или повторного пользовательского запроса. Для этого миграция `0168_provider_transition_journal` сохраняет намерение, исходное и целевое поколения, выбранные параметры, текст контекста и границу истории. В таблице допускается один незавершённый переход на диалог; изменения проверяют ожидаемые фазу, ревизию, владельца, рабочую среду и прежние настройки.

Контроллер сначала подготавливает сессию без пользовательского ввода, затем под барьером обработки событий принимает её на исполнителе. Провайдер, поколение, модель и событие нативной идентичности фиксируются одной транзакцией. После подтверждения завершения перехода снимается запрет новых отправок. Подготовка не переносит настройки сессии прежнего провайдера.

Незавершённая запись блокирует отправку, очистку контекста, изменение модели и настроек сессии, даже если процесс сервера потерял временную блокировку. Повтор с тем же ID возвращает сохранённый результат, а изменение параметров под тем же ID отклоняется. Очередь пробуждается только после завершения или подтверждённого отката.

Сверка включена в штатный фоновый цикл обслуживания. Она выбирает ограниченное число записей подключённых исполнителей и использует существующий сохранённый интервал повторов. До фиксации новой модели незавершённая подготовка отменяется. После фиксации сначала повторяется идемпотентное завершение; при потере целевой сессии исполнитель подтверждает откат, затем сервер атомарно возвращает прежние настройки. При недоступном исполнителе запись остаётся незавершённой. Удаление файлов и окончательная очистка диалога ждут освобождения сессий.

Сохранённый пакет добавляется как `agent-only` ввод к первому настоящему запросу целевой модели. После подтверждённого начала хода повторной вставки нет. Неотправленный запрос сохраняет пакет для следующей попытки через существующий механизм отложенного контекста. Явная очистка контекста исключает старый пакет. До первого запроса выбранные права и параметры читаются из журнала, без поддельного события пользовательского хода.

Проверка полного сервера обнаружила устаревшее показание контекста при смене поколения через прогретый кэш ленты. Ключ кэша теперь включает текущие провайдер и поколение; ключ исторического курсора сохраняется.

`HOST_DAEMON_PROTOCOL_VERSION` повышен с **281 до 282**: `thread.session.adopt` больше не ждёт отправки накопленных событий перед ответом. Сервер принимает сессию под барьером событий, и прежнее ожидание могло блокировать обе стороны. Остальные операции завершают отправку событий обычным способом.

## Проверка

Настоящая мигрированная SQLite используется во всех проверках хранения и серверных сценариях. Случай с резервной копией закрывает и повторно открывает базу с намерением в фазе `adopting`. Проверяются конкуренция, устаревшие ревизии, изменение поколения/модели/исполнителя, честное неизвестное окно, атомарный откат и отложенная очистка.

Серверные сценарии используют настоящее приложение и транспорт RPC с ответами на границе исполнителя. Они проверяют порядок фиксации, повтор операции, несовпадающий ответ принятия, изменившуюся историю, восстановление четырёх фаз, потерю целевой сессии, сохранённые интервалы повторов и удаление хранилища после отката. Первые отправки, недоставка, подтверждённый ход и очистка проверяются через обычный путь сообщений и обработку событий исполнителя.

Отрицательные прогоны:

- Возврат прежнего ожидания отправки событий приводит к зависшему ответу принятия в тесте с настоящим локальным процессом агента.
- Отключение доставки пакета приводит к отсутствию контекста в первой настоящей команде отправки.
- Сценарий идентичности падал до исправления нативного ID в индексируемом поле события.
- Существующая проверка равенства прогретой и холодной ленты обнаружила старое показание контекста до исправления ключа кэша.

Окончательный полный прогон прошёл: сервер **4461 passed / 3 skipped**, база **773 passed**, исполнитель **909 passed / 14 skipped**, контракт **97 passed**. Всего **6240** успешных проверок и **17** пропущенных. Окончательные сборки, типы, lint и type-aware lint прошли: **16 задач Turbo**. `git diff --check` не обнаружил ошибок.

```sh
pnpm exec turbo run test --concurrency=1 --env-mode=loose --filter=@bb/server --filter=@bb/db --filter=@bb/host-daemon --filter=@bb/host-daemon-contract
pnpm exec turbo run build typecheck lint lint:type-aware --filter=@bb/server --filter=@bb/db --filter=@bb/host-daemon --filter=@bb/host-daemon-contract
```

Источник и тесты не менялись во время Vitest. Прогоны используют изолированный Node 22.19.0, pnpm 9.15.0 и тестовые каталоги; переменные рабочего BB исключены. Журналы находятся в `.tmp/toolchain/*provider-transition*` и `.tmp/toolchain/*provider-adopt-flush*`.

Это серверная основа. Нового пользовательского действия пока нет; переключатель UI, API/SDK/CLI, предпросмотр состава истории и проверка доступного окна остаются следующим этапом. В этой проверке не получен ответ настоящей Claude/Qwen/API-модели, не проверены Linux, Safari на iPhone или VPS. Проверка карты навыка остановилась на существующей непокрытой семье CLI `diagnostics`; её базовая линия не перезаписана.
